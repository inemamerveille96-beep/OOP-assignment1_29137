## 1. Problem statement

AUCA intends to replace manual student, staff, course, timetable, assessment, fee and library records with a console-based School Management System. Develop a complete application named `AUCA_ID`. The application must manage the entities below, and demonstrate:

- encapsulation
- multilevel and hierarchical inheritance
- interfaces
- abstract classes
- polymorphism
- object relationships
- validation
- exception handling

The examiner will inspect and run the actual project physically.

Create **exactly 15 prescribed domain types**: **2 interfaces, 2 abstract classes and 11 concrete classes**. In addition, create one `Main` class and the required custom exception classes. The six attributes specified for each domain type are mandatory. Interface attributes are `public static final` constants, not per-object state; the six interface constants below are intentional. Inherited attributes count toward an object's state, but every concrete or abstract class must also declare the six attributes listed for that type.

## 4. Interface contracts and required methods

All public business operations must be declared in an interface. Implement the two required interfaces with the signatures below. Additional business operations must first be declared in the most appropriate interface before implementation; helper methods such as private validators, constructors, getters and setters are exempt. Interface methods are public and abstract unless explicitly defined as `default`/`static`.

| Interface | Required method declarations |
| --- | --- |
| `Identifiable` | `String getId();` `String getDisplayName();` `boolean isActive();` |
| `Registrable` | `void validate() throws ValidationException;` `void printDetails();` `String getRegistrationSummary();` |

Every concrete class must implement all applicable interface methods, directly or through inherited concrete implementations.

`Person` must declare `public abstract String getRoleDescription();` and `AcademicMember` must declare `public abstract String getAcademicCategory()`.

Since all public business operations must be interface-declared, add these two signatures to `Registrable` as `default` methods or declare them there as abstract and implement appropriately across all types; explain your chosen design during demonstration.

To avoid forcing non-person entities to implement person-specific operations, a cleaner alternative is to add these as abstract methods to `Person` and `AcademicMember` and treat them as the specifically permitted abstract-class extension to the interface rule.

## 5. Required inheritance and polymorphism

Implement the mandatory inheritance hierarchy:

- `Person -> AcademicMember -> Student`
- `Person -> AcademicMember -> Teacher`
- `Person -> Administrator`

This demonstrates multilevel and hierarchical inheritance.

- `Person` implements both interfaces; `AcademicMember` inherits those contracts.
- `Department`, `Course`, `Classroom`, `Enrollment`, `Assessment`, `FeePayment`, `LibraryBook` and `BookLoan` implement both interfaces directly.
- Do not attempt multiple class inheritance in Java.

Demonstrate runtime polymorphism by storing `Student`, `Teacher` and `Administrator` objects in a `List<Person>` and invoking overridden methods through `Person` references. Also store unrelated concrete entities in `List<Identifiable>` and call interface methods.

Include at least one use of `super(...)`, method overriding and constructor chaining. Explain why `Person` and `AcademicMember` cannot be instantiated directly.

## 6. Required registration workflow and object relationships

All data entry must use **one shared `Scanner`** reading from `System.in`. Store records in typed in-memory collections (for example `ArrayList`); database connectivity and GUI frameworks are not required. On registration, users must choose an existing related object from a numbered list. Never ask users to type an arbitrary related ID and silently accept an unknown record.

| Registration | Mandatory prerequisites / behavior |
| --- | --- |
| Department | Head teacher is optional at initial creation; allow assignment after a Teacher exists. |
| Student / Teacher | Department must exist; if none exists, prompt to register Department first, then resume. |
| Course | Department and Teacher must exist; show existing records and permit guided prerequisite registration. |
| Enrollment | Student and Course must exist; prevent duplicate active enrollment for same student, course and semester. |
| Assessment | Enrollment must exist; only assess an active enrollment. |
| FeePayment | Student must exist; prevent duplicate receipt numbers. |
| BookLoan | Student and LibraryBook must exist; require an available copy; update stock on loan and return. |
| Classroom / Administrator / LibraryBook | Can be created without other records. |

When a required prerequisite is missing, display a clear message, such as *"No course exists. Register a course before enrolling a student."* Offer:

1. Register prerequisite now
2. Return to menu

After successful prerequisite registration, resume the original task. Do not create placeholder students, teachers, departments or courses automatically. If the user cancels, leave the original registration uncommitted.

## 8. Validation requirements

Perform validation before storing or modifying data; repeat input until corrected or the user cancels. At minimum enforce:

- nonblank required text
- trimmed names of 2-60 characters
- unique IDs and unique student/employee/course codes
- valid email syntax and maximum length
- phone numbers containing 10-15 digits with optional leading `+`
- dates parsed with `LocalDate` and no invalid calendar dates
- date of birth in the past
- admission/hire/enrollment dates not in the future unless a justified rule is documented
- study year 1-6
- credit hours 1-6
- classroom capacity greater than zero
- floor number zero or greater
- teacher salary and payments strictly positive
- nonnegative book copy counts with `availableCopies` not exceeding `totalCopies`
- assessment `maximumScore` greater than zero and `obtainedScore` between zero and `maximumScore`
- `dueDate` after `borrowedDate`
- `returnedDate` absent until returned and never before `borrowedDate`
- allowed status, semester, assessment type and payment method values
- nonempty receipt number
- valid menu selection

Use `LocalDate` parsing with `try`/`catch`, `BigDecimal` for financial amounts and appropriate checks for `null` references. Avoid using `Scanner.nextInt()` mixed with `nextLine()`; parse complete lines to prevent skipped input.

Validate cross-record rules: a teacher must belong to an existing department, a course must reference a registered department and teacher, and a student cannot borrow a book when no copies remain.
